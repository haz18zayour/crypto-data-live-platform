# R8 — Solana On-Chain: Buy vs. Build

Research date: 2026-09-08. Session's WebSearch budget was exhausted early (200/200 used before this task's queries ran); findings below rely on direct WebFetch of vendor pages (successes and failures both reported) plus clearly-flagged prior training knowledge. Anything not confirmed live is marked **UNVERIFIED**.

## 1. Bottom line up front

1. **Network activity (active addresses, tx count, fees, TPS, staking/validators) is BUILD, and it's cheap.** Solana's free-tier RPC providers (Helius, QuickNode, Alchemy all confirmed with real free tiers) plus fully-free staking APIs (Validators.app, confirmed free with only rate limits — no pricing tier at all) are sufficient for a once-a-day batch job. Effort: low, days not weeks. Cost: $0–49/mo.
2. **SOL realized cap / MVRV is OMIT, not BUY, not BUILD.** No vendor researched — including Glassnode, CryptoQuant, Messari, Santiment (confirmed to explicitly exclude Solana as of Feb 2026), Coin Metrics (per your own probe) — sells genuine SOL MVRV at any price. Building it means reconstructing a full historical cost-basis ledger from an account-based chain with ~6 years of history and no UTXO analog to lean on; no open-source implementation was found. This is not a weekend project — realistically months of dedicated engineering, not something a solo maintainer should attempt for a dashboard's sake.
3. **SOL exchange flows are OMIT for the same reason your prior system was rebuilt: label coverage would be partial, and partial coverage that's presented as a number is exactly the "wrong data" failure mode.** Solana's exchange-wallet labeling ecosystem is materially less mature than Ethereum's. Even mature vendors with excellent labels (Glassnode, CryptoQuant) publicly disagree with each other on flow numbers for assets they've labeled for years; a self-curated Solana label set would be worse, not better.
4. Cheapest genuine path to real SOL on-chain **flow/balance data** (raw, not a computed metric) is Bitquery ($39/mo Personal plan, confirmed) or a Helius/QuickNode free-tier RPC if volumes stay low — but none of these hand you MVRV or flows as a finished metric; you'd still be building the metric yourself on raw data, which loops back to point 2/3.
5. Recommendation: **BUILD network activity now, OMIT valuation and flow metrics and render them UNAVAILABLE**, revisit only if a vendor ever publishes genuine SOL MVRV (none currently do) or if budget allows licensing a maintained label set (Nansen/Arkham) specifically for flows — expect $150–$1,800+/mo territory for that, UNVERIFIED exact current pricing.

## 3. Part B — DIY feasibility, metric class by metric class

### 3.1 Network activity (active addresses, tx count, fees, TPS, staking/validators)

**Verdict: FEASIBLE. Low effort (days), $0–49/mo.**

- Solana's own node-provisioning docs (docs.anza.xyz/operations/requirements, fetched live) specify ledger disk sizing as "1TB or larger... consider a larger ledger disk if longer transaction history is required" — confirming that a default node does **not** retain full history; retention is an operator choice, and full archival is explicitly a separate, larger commitment.
- You don't need full archival for daily network-activity aggregation: `getBlock` for the current day's slots via a free-tier RPC (Helius/QuickNode both confirmed to offer free tiers with tens of millions of credits/month) is enough to compute daily non-vote tx count, unique signer count (active addresses proxy), and fee totals for that day, run once via cron.
- Vote transactions are a real complication: Solana's consensus historically produces a very large volume of vote transactions (every active validator votes roughly every slot), which can dominate raw transaction counts. **Exact current vote/non-vote split was not reconfirmed live this session** (search budget exhausted, targeted fetches for this stat 404'd) — treat any specific percentage as UNVERIFIED. What's certain: the RPC-level distinction between vote and non-vote transactions is a standard, well-documented filter (`getBlock` responses tag transactions, and `transactionDetails` / vote-program filtering is standard practice used by every Solana explorer), so this is a filtering problem, not a scale-blocking problem, for a single day's worth of data.
- Staking/validator counts: solved for free by Validators.app (confirmed free API) and likely Stakewiz (UNVERIFIED live, but well-established).
- Effort estimate: 1–3 days to write and schedule the aggregation job (RPC calls for the day's blocks + a validator-data API call), assuming familiarity with Solana's JSON-RPC shape.

### 3.2 Realized cap and MVRV

**Verdict: NOT FEASIBLE for a solo maintainer. This is not a weekend project — realistically months of dedicated engineering, and possibly not worth it even then.**

Reasoning:
- Realized cap requires knowing the last-moved price ("cost basis") of every unit of SOL currently in circulation. On a UTXO chain (Bitcoin) this falls out naturally because every UTXO already carries its creation price. **Solana is account-based — balances are mutable, not discrete spendable outputs** — so there is no UTXO to inherit a cost basis from. You would have to reconstruct an accounting model (FIFO/HIFO/average-cost) across the **entire transfer graph since genesis** (Solana mainnet-beta launched March 2020, ~6.5 years of history as of this research date) to assign a synthetic "basis" to every lamport, then track it through every subsequent transfer, stake, unstake, and program interaction (SOL moves through countless DeFi/staking program accounts, not just wallet-to-wallet transfers).
- Scale: this session could not reconfirm a live, current total-transaction-count figure for Solana (targeted fetches to Solana's own stats pages, Wikipedia, and CoinGecko all failed to surface it) — **treat any specific number as UNVERIFIED**. What is not in dispute, and is corroborated by Solana's own node-sizing guidance (ledger sizing explicitly scales with "how much history you want," 1TB+ as a baseline for a fraction of history), is that full-history data at Solana's throughput is an archival-scale problem, not a database-scale one. Full historical ledger access at this scale is normally only practical via the Solana Foundation's own Google BigTable-backed historical archive (accessed through specific RPC methods on providers that support it), not via a standard node.
- No open-source reference implementation of a Solana realized-cap/MVRV calculation was found in this research (none surfaced despite targeted searches for a methodology or GitHub project). This contrasts with Bitcoin, where realized-cap/UTXO-age tooling is common and well-documented. The absence of prior art is itself informative: if this were a solved, low-effort problem, a vendor or open-source project would likely already publish it, given SOL's market cap and demand for the metric.
- Bottom line: this would mean building, from scratch, (a) an account-based cost-basis accounting engine with a defensible methodology, (b) an ETL pipeline capable of processing Solana's full transaction history, and (c) archival storage/compute for that pipeline — a multi-month project with real infrastructure cost, for a metric that (per Part A) no vendor at any price currently sells for SOL either. **Say plainly: this is not a weekend project, and arguably not a solo-maintainer project at all.**

### 3.3 Exchange flows

**Verdict: A self-curated label set would very likely recreate the exact "wrong data" failure this platform exists to avoid. OMIT unless a professionally maintained label set is licensed.**

- Exchange-flow metrics require a reliable, comprehensive list of exchange-controlled wallet addresses. Dune's Spellbook **does have a dedicated Solana dbt subproject** (confirmed via the Spellbook GitHub repo), meaning some community-maintained Solana decoding/labeling exists — but the fetched repo content did not surface a Solana-specific exchange-label dataset, and Solana's labeling ecosystem is widely understood (training knowledge, not reconfirmed live) to be much younger and less complete than Ethereum's: Solana exchanges rotate many hot wallets, don't publish canonical deposit-address lists the way some EVM exchanges semi-do, and cross-program wrapped/associated-token-account structures make address attribution harder than a simple wallet-to-wallet model.
- Even where labeling is mature (BTC/ETH, years of vendor investment), Glassnode explicitly documents its exchange balance figures as **lower bounds subject to retroactive revision**, and Glassnode and CryptoQuant have **publicly disagreed on the same flow event** for well-labeled assets. If two well-funded vendors with a decade of Bitcoin/Ethereum labeling still produce materially different numbers, a self-curated Solana label set — necessarily less complete — would not produce a more trustworthy number; it would produce a confidently-wrong one, which is precisely what your background note describes as the prior system's failure mode ("not degraded data, wrong data").
- Verdict: **partial coverage here is a form of the same failure**, not a lesser version of it. OMIT (render UNAVAILABLE) unless you license a maintained, professionally-curated label set (Nansen or Arkham are the two with the best-known Solana wallet-labeling reputations, per training knowledge — pricing UNVERIFIED live this session) and even then, disclose the source and its known limitations rather than presenting it as ground truth.

### 3.4 Open-source implementations available to adopt

- **Network activity**: effectively yes — the JSON-RPC vote/non-vote transaction distinction is standard, and Solana explorers (Solscan, Solana Beach, Solana's own explorer) all implement it; you're writing a thin aggregation script against a well-documented, widely-implemented pattern, not inventing anything.
- **Realized cap/MVRV**: no open-source implementation found for Solana specifically.
- **Exchange flows**: partial — Dune's Spellbook has *some* Solana decoding infrastructure to build on (confirmed the subproject exists), but no evidence of a ready-made, comprehensive exchange-label dataset for Solana was found in this research.

## 4. Part C — Recommendation

| Metric class | Decision | Detail |
|---|---|---|
| Active addresses, tx count, fees, TPS | **BUILD** | Free-tier Helius or QuickNode RPC + a scheduled job filtering vote vs. non-vote transactions. 1–3 days effort, $0/mo. |
| Staking / validators | **BUILD (trivially)** | Validators.app free API (confirmed, no paid tier exists) covers this outright; Stakewiz as a free cross-check (UNVERIFIED live but well-established). Near-zero effort. |
| Realized cap / MVRV | **OMIT** | No vendor sells it for SOL at any price found (Coin Metrics per your probe, Santiment confirmed absent, Glassnode/CryptoQuant unconfirmed-leaning-absent). Building it requires reconstructing a full historical cost-basis ledger for an account-based chain with no UTXO analog and no known open-source precedent — realistically a multi-month engineering project, not proportionate to a single-user dashboard. Render UNAVAILABLE. |
| Exchange flows | **OMIT** (or BUY only from a professionally maintained, disclosed source — Nansen/Arkham class, pricing UNVERIFIED live but expect materially more than $49/mo) | Solana's exchange-address labeling ecosystem is too immature for a self-curated set to be honest, and even mature vendors on better-labeled chains disagree with each other. Partial coverage presented as a number is a form of the exact failure this platform was rebuilt to avoid. |

**Bottom line for a solo maintainer whose goal is trustworthiness, not completeness:** build the two metric classes where the data genuinely exists and is cheap to get (network activity, staking), and render SOL's valuation and flow columns as UNAVAILABLE rather than manufacture them — either by proxying (already rejected) or by DIY-building on top of incomplete labels and unproven accounting methodology. An honest gap in the SOL column is consistent with the platform's own stated principle; a confidently-displayed, self-built approximation of MVRV or exchange flow is not.
