## Existing implementations

- **`tiagosiebler/okx-api`** (TypeScript, actively maintained, used widely as the reference for the full v5 surface) exposes each endpoint this PRD needs as a distinct typed function: `getFundingRate()`, `getFundingRateHistory()`, `getOpenInterest()`, `getContractsOpenInterestAndVolume()`, `getTakerVolume()`, `getContractTakerVolume()`, `getLongShortRatio()`, `getLongShortContractRatio()` — all public, no auth, GET-only. Confirms the shape this PRD's fetchers should mirror one endpoint per registry entry, not one combined call. https://github.com/tiagosiebler/okx-api/blob/master/docs/endpointFunctionList.md
- **`okxapi/python-okx`** — the Python reference SDK — hardcodes the same literal paths (`/api/v5/public/funding-rate`, `/api/v5/public/funding-rate-history`, `/api/v5/public/open-interest`, `/api/v5/rubik/stat/taker-volume`, `/api/v5/rubik/stat/contracts/long-short-account-ratio`) as constants, useful directly since this project's ingestion is already Python/httpx. https://github.com/okxapi/python-okx (consts.py)
- **HolySheep AI's backtesting engineering guide** is an existing practitioner writeup of exactly this PRD's funding-history ingestion problem: it hits `limit=100`/page, paginates on `fundingTime` via `after`, warns "OKX caps at 100/page" and that the total series is capped at "400 records (≈1 year for 8h funding cadence)," and separately warns that `before`/`after` pagination "is brittle for multi-symbol sweeps" — worth taking as a direct implementation constraint rather than re-discovering it via trial and error. https://www.holysheep.cn/articles/en-okx-funding-rate-history-api-for-backtesting-2026-07-12-0017.html

## Approach options

**A. OKX-only, single-venue, "uncorroborated" declared per US-306** — Fetch funding/OI/long-short/taker from OKX only, mark every derivatives registry entry as uncorroborated (structurally already legal per PRD-003/US-306). *Trade-off:* simplest, ships fastest, zero cross-venue reconciliation logic, but the registry carries a permanent "single source of truth" flag for this whole category — acceptable for a personal dashboard, not for anything claiming institutional-grade data quality. *Cost:* $0, one venue's rate limits only. *Who uses it:* small personal dashboards and single-exchange trading bots (implicit in every SDK surveyed — none of the surveyed OSS clients wrap more than one venue's derivatives endpoints in a single call).

**B. OKX primary + Coinglass (or similar aggregator) as second source for corroboration only** — OKX stays the fetched-and-displayed value; a second call to an aggregator checks the OKX number is in the same order of magnitude, without displaying the aggregator's (often modeled) number. *Trade-off:* satisfies US-306's "declare a second source" requirement with an actual second source rather than a flag, but Coinglass's own numbers for exactly this category (long/short, OI) are partly derived/modeled per this project's own prior finding on liquidations — using it even just for corroboration risks importing that same "modeled passing as measured" problem this PRD explicitly refuses. *Cost:* Coinglass free tier is rate-limited and its API terms/availability weren't verified in this pass — flag as **UNVERIFIED**, needs its own reachability check before committing. *Who uses it:* aggregator-dependent retail dashboards (Coinglass's own product is the canonical example of this pattern, per the coinglass.com references surfaced throughout this research pass, e.g. https://www.coinglass.com/exchanges/OKX).

**C. Two-venue direct: OKX + a genuinely reachable second exchange (e.g. Coinbase or Kraken derivatives, if they expose funding/OI at all), fully independent fetch-and-compare** — the gold-standard version of what PRD-003 asks for. *Trade-off:* Coinbase and Kraken's perpetual/derivatives products and public API surface for funding/OI/long-short were **not verified in this research pass** — this project's existing architecture doc only measured their *spot* OHLCV reachability, not their derivatives endpoints, so this option carries real unresolved risk that a second venue simply doesn't expose these fields publicly. *Cost:* unknown until endpoint existence is confirmed. *Who uses it:* institutional data vendors (Kaiko, Amberdata), not solo/small-team dashboards, per the general pattern across every practitioner source surveyed.

**Recommendation: Option A now, structured so Option B/C is a additive registry-entry change later.** Every source found in this pass — the SDK doc, the backtesting guide, OKX's own docs — treats OKX's derivatives surface as complete and self-consistent for BTC/ETH/SOL/BNB perpetuals; no second venue's derivatives endpoints were confirmed reachable or even existent in this research window, and PRD-003/US-306 already makes "declared uncorroborated" a legal, non-blocking state rather than a gap that has to be silently papered over.

## Edge cases and gotchas

- **The historical funding-rate endpoint carries no interval field — you must derive it from consecutive `fundingTime` deltas, or you will silently inherit the annualization bug this PRD exists to prevent.** OKX's own guidance for the *current* interval points to a *different* endpoint (`GET /public/funding-rate`, the live one this PRD deliberately does not fetch for display) or the web UI — nothing in the settled-history payload states the interval directly. A naive implementation that fetches `funding-rate-history` and assumes 8h will be wrong for exactly the tiered instruments OKX names by name. https://www.okx.com/en-us/help/okx-to-enable-automatic-updates-for-funding-fee-settlement-period
- **Backtesting-focused engineering writeups treating OKX in 2026 still hardcode "8h" without checking it.** The most detailed practitioner guide found in this pass — written specifically about funding-rate history for backtesting — states flatly "Funding rate — settled every 8 hours" as a fixed constant throughout its examples, with zero handling for interval changes. This is a live demonstration that the exact bug this PRD's adversarial case targets is not a hypothetical — a specialist writeup published in 2026 makes it. https://www.holysheep.cn/articles/en-okx-v5-api-yanshengpin-funding-rate-yu-mark-price--2026-07-18-0005.html
- **`funding-rate-history` is capped at 400 records total (≈1 year at 8h cadence), not a rolling window you can page through indefinitely, and pagination via `before`/`after` is "brittle for multi-symbol sweeps."** For BNB or other lower-liquidity instruments whose interval sometimes drops to 1h, 400 records covers far less real time than a year — the retention window is record-count-based, not time-based, so an instrument's own switch to a shorter interval silently shrinks its available history depth. https://www.holysheep.cn/articles/en-okx-funding-rate-history-api-for-backtesting-2026-07-12-0017.html
- **OKX's escalation ladder both tightens (8h→4h→2h→1h) *and* reverts, based on a rolling 12-hour lookback of settlements within ±0.20%** — meaning a single instrument can legitimately show 8h, 4h, 1h, then back to 8h within weeks. Any registry design that treats "funding interval" as a fixed per-instrument attribute set once at onboarding will drift stale silently. https://www.okx.com/en-us/help/okx-to-enable-automatic-updates-for-funding-fee-settlement-period
- **Binance's HTTP 451 to US IPs applies to unauthenticated, no-auth-required public market-data calls specifically on the futures/derivatives API (`fapi.binance.com`)**, not just trading/account endpoints — confirming this PRD cannot fall back to Binance for derivatives from the same US GitHub-hosted compute already chosen for the rest of the project, reinforcing rather than merely repeating the existing architecture decision. https://dev.binance.vision/t/error-451-when-accessing-the-futures-api-from-us/16725

## Blind spots

1. **The registry's "funding interval" field will be correct at write-time and wrong by the next fetch if the escalation/de-escalation ladder isn't re-checked on every ingest, not just at onboarding.** OKX's mechanism explicitly reverts after 12 hours of stable settlements — a field set once and never re-derived from live `fundingTime` deltas will drift the same way the prior system's "confident 0.0" drifted, just more subtly, because it will look plausible rather than obviously blank.
2. **`rubik/stat` endpoints (OI-volume, long-short-ratio, taker-volume) were not confirmed in this research pass to distinguish linear from inverse contracts in their response payload the same way `open-interest`/instrument IDs do.** If the aggregate stat endpoints blend `instType=SWAP` across both margin types under the hood — which was not ruled out here — the unit-mixing trap this PRD names explicitly for raw OI could reappear one layer up, inside an OKX-computed ratio the fetcher never gets to inspect or split.
3. **Nobody has checked whether OKX's rate limits on the `rubik/stat` family (distinct from the 20 req/s figure confirmed only for the public funding endpoint) can sustain four assets × four metrics on the existing GitHub Actions cron cadence without throttling** — a throttling failure here would not look like an outage, it would look like intermittently missing rows, which is exactly the failure mode PRD-005's completeness matrix was built to catch, but only if this PRD's fetchers report it as missing rather than silently retrying into a 429 that gets treated as a transient error and dropped.
