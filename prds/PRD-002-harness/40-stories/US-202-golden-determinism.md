As the owner, I want each indicator pinned to a committed golden value, at least one of which
was computed outside this codebase, so that a wrong-but-consistent result cannot be blessed as
correct.

US-006 is the cautionary case: it passed **6/6**, verified by a different vendor, while storing
a Hong Kong day close as a UTC one. A golden generated by the code under test would have
recorded 78,834.1 as "correct" permanently, and every future run would have agreed.

## Acceptance criteria

- [test: each golden file records where its expected value came from] A `source` field naming hand arithmetic or a published reference vector; a golden with no provenance fails the suite
- [test: at least one golden per indicator family is externally computed] Marked `external`, and the suite fails if none is
- [test: recomputing from the stored input bars reproduces the golden exactly] Exact float equality — inputs are fixed and the code is deterministic, so any drift is a real change
- [test: a changed computation fails the golden rather than updating it] There is no regenerate-on-run path; updating a baseline is a deliberate committed edit
- [cmd: uv run pytest tests/test_goldens.py -q --no-header -o addopts= --tb=short] The golden suite runs and passes on its own

## Notes for the implementer

- Goldens are small committed JSON: the input bars, the parameters, the expected output, and
  the `source` of that expectation.
- **Do not add a `--force-regen` style flag.** Snapshot tooling that rewrites baselines trains
  the reader to accept changes blindly, and a snapshot cannot explain *why* an output is
  correct — the reviewed baseline is the entire oracle. Regenerating is how US-006's bug would
  have become permanent.
- The externally-computed golden is the point of this story. Hand-compute an EMA or RSI over a
  handful of bars, or take a published test vector, and say so in the `source` field.
- Keep bar counts small enough that a human can check the arithmetic.
