## Existing implementations

Real dashboards separate the exact three metric classes this PRD does:

- **The Block** and **Token Terminal** both publish "Non-vote transactions on Solana" as a distinct series from raw transaction count, precisely because raw counts are consensus noise, not user activity — both are downstream evidence that shipped implementations treat vote-filtering as necessary, even though the raw RPC gives no server-side lever for it: [theblock.co/data/on-chain-metrics/solana/non-vote-transactions-on-the-solana-network-daily-7dma](https://www.theblock.co/data/on-chain-metrics/solana/non-vote-transactions-on-the-solana-network-daily-7dma), [tokenterminal.com/explorer/projects/solana/metrics/non-vote-transaction-count](https://tokenterminal.com/explorer/projects/solana/metrics/non-vote-transaction-count).
- **Solscan's own analytics dashboard** exposes "vote vs non-vote transactions" as a first-class split view, again implying client-side classification against fetched blocks rather than a filtered RPC call: [analytics.solscan.io/overview/transaction/vote-vs-non-vote-trans](https://analytics.solscan.io/overview/transaction/vote-vs-non-vote-trans).
- **UNVERIFIED** (own recall, not confirmed by a fetched source this pass): the standard client-side technique is to inspect each transaction's account keys / program invocations for the vote program address `Vote111111111111111111111111111111111111111` and classify a transaction as a vote iff every top-level instruction targets that program. This needs direct confirmation against Solana's program docs or a working reference implementation before it becomes a story's acceptance criterion — flagged as a research gap below, not a settled fact.
- **Coin Metrics' own Python/R clients** (`coinmetrics-api-client`) wrap the same public `/v4` community endpoints this PRD would call directly via httpx — evidence the free tier is treated as production-usable by Coin Metrics itself, not a crippled trial: [github.com/coinmetrics/docs-website](https://github.com/coinmetrics/docs-website).

## Approach options

**1. Coin Metrics Community API, direct httpx, for BTC/ETH (and BNB if confirmed) — recommended for the on-chain fetch.**
How: daily batch call to `/v4/timeseries/asset-metrics` for `CapMVRVCur`, `AdrActCnt`, exchange-flow metrics, one asset per call to respect the ~1.6 req/s ceiling. Cost: $0. Trade-off: rate limit means a 4-asset × 3-metric daily batch (12 calls) takes ~7+ seconds minimum if serialized correctly — trivial for a once-daily job, but a naive concurrent implementation will get 429'd. Who uses it: Coin Metrics' own community client library is built on exactly this endpoint set ([github.com/coinmetrics/docs-website](https://github.com/coinmetrics/docs-website)).

**2. Helius free-tier RPC for SOL network activity — recommended for the build side.**
How: `getBlock` per slot (or `getSignaturesForAddress`/batch RPC) at a sampled cadence, client-side vote-filtering, aggregated to daily non-vote tx count + unique signers. Cost: $0 within 1M credits/mo, 10 req/s ceiling ([helius.dev/docs/billing/rate-limits](https://www.helius.dev/docs/billing/rate-limits)). Trade-off: no server-side vote filter exists at all ([github.com/solana-labs/solana/issues/29856](https://github.com/solana-labs/solana/issues/29856)) — every block's full transaction list must be pulled and filtered locally, which is real client-side compute and credit cost, not "free" in the way R8 characterized it.

**3. QuickNode free tier as the Solana RPC alternative.**
How: same interface as Helius, different provider. Trade-off: R8 did not load-test either against this project's real batch shape, and this research pass did not re-test it either — this remains a genuine open decision, not a settled one. Cost: $0 documented free tier exists, per [quicknode.com/builders-guide/best/top-10-free-rpc-endpoints-for-developers](https://www.quicknode.com/builders-guide/best/top-10-free-rpc-endpoints-for-developers).

**4. Validators.app for SOL staking/validator data — recommended, only option researched with a confirmed no-paid-tier posture.**
How: token-gated GET requests against their REST API for validator count, commission, active stake. Cost: $0, but capped at 20–40 requests/5 min depending on endpoint, with a mandatory account + API token, not a fully anonymous free tier ([validators.app/api-documentation](https://www.validators.app/api-documentation)) — a materially stricter free tier than Coin Metrics' anonymous-by-IP model.

**Recommendation:** Coin Metrics Community API (option 1) for BTC/ETH/BNB-if-confirmed, Helius free tier (option 2) for SOL network activity, Validators.app (option 4) for SOL staking. This matches R8's build-don't-buy verdict and every number above is now sourced rather than catalog-asserted — one line of justification: **it's the only combination where every claimed "free" limit has a live-fetched number attached to it (rate limit, credit cap, or req/5min cap), not a vendor marketing page.**

## Edge cases and gotchas

- **The vote-filter gotcha is worse than "unconfirmed" — it's a myth to retire.** R8 phrased this as "a filtering problem, not a scale-blocking problem," implying some RPC-level knob exists to flip. It doesn't: `getBlock` has never supported vote exclusion, and the 2022 feature request for it was explicitly rejected ([github.com/solana-labs/solana/issues/29856](https://github.com/solana-labs/solana/issues/29856)). Any story that says "confirm the RPC-level filter works as documented" is testing something that was never documented to exist. The story needs to specify client-side vote-program-instruction classification instead, and that classification logic itself needs a cited reference before being written into an acceptance criterion — currently it is only this document's UNVERIFIED recall.
- **Coin Metrics' rate limit is per-IP, not per-key** — a GitHub Actions runner's ephemeral IP means the limit resets cleanly run-to-run, but also means it cannot be "banked" or monitored via a dashboard; a burst of concurrent asset/metric calls at the start of a batch job will 429 silently unless serialized with backoff (10 req/6s ≈ 1.6 req/s — [coinmetrics.readthedocs.io/en/latest/community.html](https://coinmetrics.readthedocs.io/en/latest/community.html)).
- **Validators.app requires a verified account and per-endpoint rate ceilings** — this is a materially different trust/provisioning model than Coin Metrics' anonymous-by-IP approach, and the brief's framing of R8's "confirmed genuinely free" undersold the friction: a token must be provisioned and stored as a secret before US-0xx work can even start ([validators.app/api-documentation](https://www.validators.app/api-documentation)).
- **Helius free-tier per-method sub-caps can bite even under the 10 req/s headline number** — `getProgramAccounts` is capped at 5/s and DAS calls at 2/s regardless of the 10 req/s overall ceiling; if the SOL story ends up needing `getProgramAccounts` for anything (e.g. enumerating stake accounts as a cross-check against Validators.app), that path is throttled tighter than the naive "10 req/s, fine" read of the plan ([helius.dev/docs/billing/rate-limits](https://www.helius.dev/docs/billing/rate-limits)).
- **BNB coverage is still an assumption, not a fact, after this research pass.** Neither fetched Coin Metrics page lists per-asset metric availability; the only way to settle it per the brief's own instruction is a live, one-metric-at-a-time probe against `/v4/timeseries/asset-metrics?assets=bnb&metrics=CapMVRVCur` etc. — this document did not execute that probe and it must happen before `20-decisions.yaml` is written, or BNB coverage remains catalog-asserted exactly as R2 originally warned against for SOL.

## Blind spots

1. **The vote-filter myth could already be baked into a story's acceptance criteria before anyone notices it's wrong.** The brief itself asked to "confirm the RPC-level filter works as documented" — but no such filter was ever documented, only requested and rejected. If `30-spec.md` is drafted from the brief's framing without reading this document, a story could be written expecting a `votes: false` parameter that has never existed, guaranteeing an implementer attempt burns itself against a nonexistent API surface — precisely the "tripwire fires identically every attempt" failure mode already logged for this project.
2. **Validators.app's mandatory account/token requirement is a provisioning dependency the brief characterized as frictionless ("confirmed genuinely free, no paid tier exists at all").** Free and frictionless are not the same thing — someone has to create an account, generate a token, and store it as a GitHub secret before the first SOL-staking story can even attempt a live call. If that provisioning step isn't scheduled as its own explicit prerequisite, a story will fail on missing credentials and look like a code defect.
3. **Nobody has re-run R2's exact live BNB probe in this research pass.** This document flags the gap honestly, but the risk is that the gap gets treated as "researched" simply because this document exists and discusses BNB at length — it does not contain a single fetched number confirming or denying BNB coverage. If `20-decisions.yaml` is written from this document's prose without someone actually running the probe, BNB coverage becomes exactly the kind of catalog-page assumption R2 explicitly warned against.
