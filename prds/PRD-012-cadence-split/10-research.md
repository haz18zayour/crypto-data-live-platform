## Existing implementations

No public reference implementation matches this exact shape (multi-tier crypto-indicator collection split across GitHub Actions cron tiers with a separate contract-canary heartbeat), but the individual pieces are each well-trodden:

- **GitHub Actions as a scheduler for data pipelines** is a widely-documented pattern, but every serious writeup converges on the same caveat this PRD must design around: treat `schedule:` "as a trigger source, not the clock" for anything time-sensitive, and prefer running the real clock in an external scheduler (cron-job.org, EventBridge, etc.) that fires `workflow_dispatch`/`repository_dispatch` — GitHub Actions supplies compute, not punctuality. https://crontap.com/blog/github-actions-cron-drift-problem
- **cron-job.org + `repository_dispatch`** is exactly the pattern this repo's own architecture doc already committed to as the "independent second trigger" for `ingest` — this PRD's fast tier is a natural extension of an already-adopted pattern, not a new integration.
- **Healthchecks.io "one check per job" with per-check Grace Time** is the vendor's own documented best practice for exactly this problem (multiple independently-scheduled jobs each needing their own dead-man's-switch): https://healthchecks.io/docs/configuring_checks/

## Approach options

**Option A — Three separate GitHub Actions workflows (fast/medium/daily), each with its own `cron:` and its own `HEALTHCHECKS_PING_URL_*`**
How it works: split `ingest.yml` into `ingest-fast.yml` (`*/5 * * * *`, the 12 five-minute OKX rows), `ingest-medium.yml` (8-hour cron, the 4 funding-rate rows), and `ingest-daily.yml` (renamed current job, the 54 daily rows). Each filters the registry by its own tier at runtime (`expected_update_interval_seconds` already exists as the discriminator — no new registry field needed).
Trade-offs: Simplest to reason about; reuses the exact `expected_update_interval_seconds` field the registry already carries. But the fast tier inherits GitHub's documented 5-minute-minimum + peak-hour drift risk (https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#schedule) — a run landing 15 minutes late against a 600s freshness-warn bound (`btc_open_interest` etc.) means the cell reads `WARN`/`STALE` through no fault of the vendor or the code, purely GH Actions queue congestion at top-of-hour.
Cost: $0 (same GH Actions free-tier minutes budget, just redistributed across three workflows instead of one — total call volume is unchanged, only its clustering).
Who uses it: This is the "just use GH Actions schedule directly" default seen across most GH-Actions-as-cron writeups; it's the cheapest to build and matches what `sol-active-addresses.yml` already precedent-sets (dedicated workflow per tier).

**Option B — Same three-tier split, but the fast tier is triggered by cron-job.org → `repository_dispatch` instead of native GH Actions `schedule:`**
How it works: identical job bodies to Option A, but `ingest-fast.yml` drops its `schedule:` trigger entirely and listens only for `repository_dispatch` (type e.g. `ingest-fast`); a cron-job.org job fires that dispatch every 5 minutes.
Trade-offs: Removes GH Actions' documented top-of-hour congestion risk for the tier that actually can't absorb a 15-minute miss (600s/450s freshness bounds). Costs one more moving part (a cron-job.org job to configure and monitor) but the project's architecture doc already adopted cron-job.org as the fallback trigger for exactly this reason. cron-job.org itself is not zero-drift either (4–40s dispatch delay, https://cron-job.org/en/faq/) but that is two orders of magnitude tighter than GH Actions' reported 5–30+ minute peak drift.
Cost: $0 (cron-job.org free tier).
Who uses it: This is precisely the pattern the crontap writeup recommends for any schedule tighter than hourly (https://crontap.com/blog/github-actions-cron-drift-problem), and matches this project's own architecture-doc precedent of cron-job.org as "an independent second trigger."

**Option C — Keep one combined job, add a `--tier` flag, and just tighten the single cron to run more often**
How it works: don't split workflows; instead call the existing `ingest` entrypoint every 5 minutes but have it internally skip any indicator whose `expected_update_interval_seconds` hasn't elapsed since its last write (idempotent no-op for daily/medium rows most runs).
Trade-offs: Avoids multiplying workflow files, but every run — even the ~283 out of 288 daily runs per day that do nothing — still pays the fixed CI overhead (checkout, `uv` setup, DB connection) for zero benefit, and a single job now has to reason about mixed timeout budgets (the fast tier's OKX calls plus a daily row's occasional TA-Lib recompute in the same process). This directly risks recreating the known "a live fetch that fits its API budget can still break a scheduled job on wall-clock time alone" failure mode already logged against this exact codebase — a slow daily-tier fetch inside a job now running every 5 minutes shrinks the effective timeout budget for the fast tier sharing that same run.
Cost: $0, but wastes the most GH Actions minutes of the three options (288 daily invocations vs. Option A/B's daily job running once).
Who uses it: Not found in any external writeup for exactly this reason — the "one flexible cron, skip internally" pattern is a known anti-pattern once tiers diverge by more than ~10x in frequency, which this registry's 300s vs 86400s split (288x) clearly does.

**Recommendation: Option B.** The 5-minute tier's own freshness contract (450s stale bound) cannot absorb GH Actions' own documented delay behavior at that cadence, and the project has already adopted cron-job.org as a trigger mechanism for exactly this reason — Option B is a small, already-precedented extension, not new infrastructure. The 8-hour and daily tiers can stay on native GH Actions `schedule:` (Option A) since a 15–30 minute drift is immaterial against a 43200s/108000s freshness bound.

## Edge cases and gotchas

- **The wall-clock-vs-rate-limit distinction already bit this exact codebase once** (Helius/Solana fetch measured against credit budget but not against the CI job's own 10-minute timeout, taking 2.5h against a 10-minute limit). The current `ingest.yml` has `timeout-minutes: 10` (confirmed by reading the file). Splitting into a 5-minute-cadence fast-tier job means that job's *own* wall-clock budget must be far under 5 minutes end-to-end (checkout + `uv` install + 12 OKX calls + writes), or successive scheduled runs will start overlapping/queueing — verify this with a real timed run, not an estimate, exactly as the prior incident's fix note prescribes.
- **OKX's public market-data rate limit is per-IP, not per-account**, and open-interest specifically is rate-limited at roughly 20 requests per 2 seconds (community-sourced, OKX's own per-endpoint doc page did not resolve the number directly on fetch — flagging this as **UNVERIFIED at the primary-source level**, sourced instead from a secondary aggregator). At 12 five-minute-tier rows × one call each, this PRD's fast tier is nowhere near that ceiling even before considering that GitHub-hosted runner IPs are already ephemeral per-run (see table above) — so the brief's stated worry about "multiplying rate limits across separate runner IPs" does not hold on the numbers found; the real constraint is wall-clock timeout, not rate limit.
- **GH Actions top-of-hour congestion is not evenly distributed** — delays cluster specifically "at the start of every hour" per GitHub's own docs. A fast-tier cron of `*/5 * * * *` hits every hour-boundary by construction, so if the medium/daily tiers are *also* scheduled near `:00`, all three tiers' worst-case-drift moments coincide. Stagger daily/medium cron minutes away from `:00`/`:05` (GitHub's own recommendation: "schedule your workflow to run at a different time of the hour," https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#schedule) — the existing `ingest.yml` already does this (`cron: '17 */6 * * *'`, offset 17 minutes), so this practice just needs to be preserved, not newly invented, when the workflow is split.
- **A public repo's scheduled workflow auto-disables after 60 days of no repository activity** (GitHub's own docs, confirmed above) — worth noting for whichever new workflow file is least likely to see commits touching it, though this repo is presumably private and this is likely moot; **UNVERIFIED** whether the repo is public or private from research alone.

## Blind spots

1. **The brief's own stated worry (rate-limit multiplication across runner IPs) is the wrong risk, and the real risk it's gesturing at — wall-clock timeout collision under a tightened cadence — is the one that has *already caused a production incident in this exact codebase* (the Helius 2.5h-vs-10min timeout). Nobody has yet stated a wall-clock budget for the *new* fast-tier job specifically; without a real timed dry run, the same class of bug (works in isolated testing, breaks against the scheduler's actual clock) is one dry-run away from recurring.**
2. **Splitting `ingest.yml` into three workflow files without splitting `contract-canary.yml`'s vendor list means a canary shape-check can pass while a fast-tier write job silently fails** (e.g. wrong tier filter drops a row from every fast-tier run) — the canary checks endpoint *shape*, not that the correct *set* of rows was actually written by the correct job on the correct cadence. The adversarial case in the brief (force a fast-tier cell stale) tests exactly this, but only if someone remembers to also test "does the daily job's tier filter now silently swallow a row it shouldn't."
3. **No one has checked whether OKX's rate limit counts *scheduled polling cadence itself* as abusive** (bot-detection / ToS interpretation) separately from the raw requests-per-second ceiling — a 5-minute-cadence automated poll running indefinitely is a very different traffic pattern from ad-hoc human API usage, and OKX's API Agreement (https://www.okx.com/en-us/help/okx-api-agreement) was not read in depth during this research; **UNVERIFIED** whether continuous 5-minute automated polling of public endpoints violates any usage-pattern term distinct from the numeric rate limit.
